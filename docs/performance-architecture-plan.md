二、性能预算拆解

（一）60fps 帧预算

1. 单帧总时间为 1000 / 60 = 16.67ms。
2. 低端 4 核设备不能按 16.67ms 用满设计，建议混合帧的工程预算如下：
3. 输入事件与调度入队：不超过 1ms。
4. 主线程业务函数切片：不超过 4ms。
5. Svelte 可见区域状态提交与 DOM 更新：不超过 3ms。
6. Style、Layout、Paint、Composite：不超过 6ms。
7. postMessage 处理、结构化克隆、GC 与抖动余量：约 2.67ms。
8. 滚动帧中，主线程业务切片应降为 0 到 1ms，把预算优先让给输入、滚动、样式、绘制和合成。
9. 主线程任何一次可归因于业务调度的连续阻塞，目标不超过 5ms，硬上限不超过 8ms；绝对不允许出现 50ms 以上 Long Task。
10. Long Task API 只能报告超过 50ms 的任务，无法证明 60fps；即使没有 Long Task，也仍可能出现 20 到 40ms 的掉帧，因此必须同时统计每帧时长。

（二）600 个函数的原始工作量

1. 85% 对应 600 × 0.85 = 510 个快函数。
2. 10% 对应 60 个中等函数。
3. 明确的长尾函数有 3 个。
4. 仍有约 27 个函数没有被题面分布严格覆盖，必须作为未知风险预留。
5. 510 个快函数按小于 1ms 的上界估算，串行总耗时小于约 510ms。
6. 60 个中等函数的串行范围为 300 到 3000ms，区间中点为 1650ms。
7. 3 个长尾函数的串行范围为 150 到 600ms，区间中点为 375ms。
8. 若快函数按 0.8ms 的保守 p95 估算，则已知函数串行量约为 408 + 1650 + 375 = 2433ms，尚未计入 27 个未知函数、依赖等待、克隆、GC 和 DOM 更新。
9. 如果把 60 个中等函数和 3 个长尾函数交给 3 个 Worker，理想计算下界约为 2025 / 3 = 675ms。
10. 快函数留在主线程并按 4ms 切片执行，计算量约 408 到 510ms，另需计入 100 次以上让出事件循环的开销。
11. 理论墙钟时间至少受 max(关键路径时长, 并行工作总量 / 可用Worker数, 主线程工作总量) 约束，不能只看函数总耗时。
12. 如果串行工作比例用 s 表示，3 个 Worker 的理论加速比为 1 / (s + (1 - s) / 3)；当 s = 0.3 时只有 1.875 倍。这里的 s 必须由真实 DAG 测量，不能用“30% 的边”直接代替。

（三）线程与任务切片预算

1. 4 核设备建议 Worker 数为 min(navigator.hardwareConcurrency - 1, 3)，常规最多 3 个，主线程专门负责输入、DAG 协调、状态提交和表格绘制。
2. 页面空闲且执行 A 模式时可使用 3 个 Worker；滚动中或 B 模式连续输入时，可只让 2 个 Worker 启动新任务，给主线程和合成线程保留资源。
3. 主线程执行任何函数前先读取 performance.now()，只有在“已用时间加函数 p95 估计加 0.5ms 安全余量”仍低于切片 deadline 时才执行。
4. 小于 1ms 的快函数适合主线程批量切片；5ms 以上、输入可克隆、无 DOM 依赖的纯函数优先进入 Worker。
5. 50 到 200ms 的长尾函数不允许进入主线程调度队列，除非需求方明确无法使用 Worker 且允许重构内部循环。
6. Worker 中不要把一个 50ms 长尾任务和多个短任务打成不可抢占的大批次，避免长尾阻塞后续高优先级结果。
7. 主线程切片使用 MessageChannel 或 scheduler.yield()，并对后者做特性检测；不要依赖 setTimeout(fn, 0)，因为嵌套定时器存在 clamp 和调度延迟。

（四）Worker 通信预算

1. 每个动画帧内，主线程处理 Worker 消息、反序列化和结果入缓存的总时间建议不超过 0.5 到 1ms。
2. 初始经验阈值可设为单条消息 20 到 50KB、每帧总量不超过 100KB，但这不是浏览器常量，必须在目标真机上用实测结构化克隆吞吐校正。
3. 科学的阈值公式是：最大克隆字节数等于“可接受克隆毫秒数”乘以“目标设备上的实测 MB/ms 吞吐”。
4. Worker 卸载收益应满足：节省的主线程时间明显大于两端克隆、队列等待和提交成本；初步要求克隆耗时不超过计算耗时的 20%。
5. 小于 1ms 的函数不应跨 Worker，通信成本可能高于计算本身。
6. 大型 ArrayBuffer 或 TypedArray 优先使用 transfer list，但转移后主线程对象失效，不能继续读取或复用。
7. 普通对象、Map、Set、表格行数据使用结构化克隆；函数、DOM 节点、Svelte proxy、Symbol、WeakMap 等不能按业务对象直接传递。
8. Worker 返回结果不应逐个写入 $state，应先进入普通 pending cache，再由每帧一次的统一提交进入 Svelte。

（五）5000 行表格预算

1. 假设视口高度 800px、行高 32px，一屏约 25 行；加上下行 overscan，实际挂载 40 到 60 行即可。
2. 若每行 10 个单元格，虚拟窗口约为 400 到 600 个单元格节点；直接渲染 5000 行通常会产生数万节点，初始布局、内存和 Svelte 协调成本都不可控。
3. 滚动事件本身只记录位置并通过 requestAnimationFrame 换窗，不在滚动回调中执行 DAG、过滤、排序或重排数据。
4. 滚动帧中 Svelte 更新只应发生在可见窗口，目标不超过 2 到 3ms。
5. 表格数据层保存完整 5000 行普通数据，响应式层只保存可见窗口和必要状态，不能把完整 5000 个代理对象都纳入每轮更新。
6. 稳定行 ID 是强制项，keyed each 必须使用业务 ID，不允许使用数组索引作为滚动、更新和复用身份。
7. 如果业务坚持渲染全部 DOM，可把 CSS content-visibility 作为降级手段，但它只能降低部分绘制成本，不能消除节点内存、Svelte 更新和大规模 Layout 的根因。

（六）每字符触发预算

1. 输入事件处理函数只做读取输入、创建 runId、入队和使旧 run 失效，目标不超过 1 到 2ms。
2. 输入框字符回显必须立即发生，不能等待业务子集完成。
3. 每个字符都必须创建一轮调度记录，这保持 B 的原始语义；内部取消旧 run 不等于防抖，也不是跳过触发。
4. 旧 run 的 Worker 结果返回时，如果 runId 不是当前 run，必须丢弃；有副作用的函数不能仅凭 runId 回滚外部世界。
5. B 模式的结果延迟 SLA 题面未给；若单轮子集包含 200ms 长尾，则不可能在每个字符后 16.7ms 内保证完整结果，只能保证输入不卡、旧结果不覆盖新结果、最新结果完成后立即提交。
6. 建议把交互确认目标设为 INP p95 小于 100ms，硬门槛不超过浏览器“良好交互”常用的 200ms；最终阈值仍需需求方确认。

三、候选方案与最终选型

（一）方案一：主线程宏任务时间切片

1. 做法是在主线程维护 DAG ready queue，用 MessageChannel、scheduler.yield() 或特性检测后的宏任务循环，每次执行 4ms 左右就让出事件循环。
2. 适用性最好的是 510 个小于 1ms 的快函数、需要访问 DOM 的函数、结果很小且 Worker 通信不划算的函数。
3. 优点是没有结构化克隆、没有 Worker 启动成本、函数可以访问主线程环境、迁移成本低。
4. 失效场景是 3 个 50 到 200ms 的同步长尾；一旦函数开始执行，宏任务切片无法从函数外部打断，仍然会卡满整个函数。
5. 连续输入和滚动时，如果切片 deadline 过于激进，会持续占用主线程；如果过于保守，A 模式完成时间会拉长。
6. 迁移成本低，应作为快函数和主线程专属函数的执行通道，但不能作为整体 CPU 并行方案。

（二）方案二：requestIdleCallback

1. 做法是把低优先级计算放入浏览器声明的空闲时间，并通过 timeout 避免无限延后。
2. 适合应用启动后的 Worker 预热、安全缓存、非关键统计、下一输入概率较高数据的预计算。
3. 优点是浏览器原生、不增加依赖、语义上明确表示“空闲时再做”。
4. 失效场景是用户持续输入或持续滚动时，空闲窗口可能很短甚至长期不存在；timeout 到期还可能把任务塞回交互高峰期。
5. 空闲 deadline 即使理论上较长，也不能一次性执行 50ms 以上任务，否则会把后续输入变成卡顿。
6. 不同浏览器的空闲调度行为需要按目标环境验证，不能作为唯一调度机制。
7. 迁移成本低，但只能作为辅助通道，不能承担长尾和 SLA 任务。

（三）方案三：手写 postMessage Worker 池协议

1. 做法是使用 Vite 原生支持的 module Worker，维护 2 到 3 个 Dedicated Worker，主线程实现 DAG 协调器和类型化消息协议。
2. 消息可以分为 run、cancel、result、error、progress、shutdown 等判别联合类型，字段包含 runId、batchId、nodeId、输入、transfer list、耗时和错误信息。
3. Worker 内部按函数 ID 注册纯函数，不接收函数闭包；共享业务代码必须写成同构 TypeScript 模块。
4. 最适合 3 个长尾函数和 60 个 5 到 50ms 的纯 CPU 中等函数，可以把阻塞从主线程移走。
5. 优点是真正利用多核，主线程即使在 Worker 计算时仍能响应输入和滚动；不需要 Comlink，手写协议即可满足 strict TypeScript。
6. 缺点是输入输出必须结构化克隆或 transfer，函数不能访问 DOM，错误边界、取消、Worker 启动、内存重复都要自行处理。
7. Worker 内同步函数执行时，cancel 不能中断已经开始的 200ms CPU 循环；只能阻止其结果提交、终止空闲 Worker 或要求函数源码支持合作式取消。
8. 迁移成本中等，需要建立函数注册表、可传输数据模型、DAG 运行时和错误模型；这是当前硬约束下最现实的 CPU 卸载方案。

（四）方案四：SharedArrayBuffer 加 Atomics

1. 做法是把输入输出放入共享内存，使用 Atomics 做同步、等待、通知，配合环形缓冲区传输数据和任务。
2. 优点是可减少大对象结构化克隆，适合二进制数组、音视频数据、矩阵、大规模数值计算等稳定二进制 payload。
3. 对 600 个业务函数的一般对象结果，需要自定义序列化、布局、版本号和环形缓冲协议；复杂度明显高于普通 postMessage。
4. Svelte 状态仍然必须存在于主线程的响应式对象或 SvelteStore，不能让组件直接把 SharedArrayBuffer 上的裸内存当作普通 rune 状态反复修改。
5. COOP 与 COEP 必须正确配置；crossOriginIsolated 不可用时要完整回退，不能静默降级成一个表面正常但没有并行能力的系统。
6. Vite dev server 必须为主文档、Worker、HMR、静态资源提供兼容隔离的 headers；跨域资源需要 CORP/CORS/Credentialless 策略，HMR 很可能因隔离策略出现兼容性问题。
7. Atomics.wait 绝不能在主线程使用；设计错误会造成死锁、数据竞争、可见性顺序问题和极难排查的内存不一致。
8. 迁移成本高，且当前题面没有证明通信是主要瓶颈，因此不应作为首选。只有在真实二进制 payload 使 postMessage 克隆成为前几名瓶颈时，再局部引入。

（五）方案五：主线程合作式分块加算法重写

1. 做法是改造长尾函数内部循环，每隔固定数量迭代检查 deadline 或取消标志，把中间状态保存后让出，再由后续任务恢复。
2. 如果 3 个长尾函数源码可改且算法天然分块，这是避免 Worker 边界和复制成本的强力方案。
3. 它无法替代 Worker，因为即使每块只有 4ms，DAG 中多个分块仍在同一个主线程上与输入竞争，只能保证不出现长任务，不能创造多核算力。
4. 如果长尾算法无法保存中间状态，checkpoint 成本可能超过计算收益。
5. 对纯黑盒第三方同步函数，主线程没有抢占机制，本方案不成立。
6. 迁移成本取决于源码；应作为长尾在 Worker 中也需要取消能力时的内部实现，而不是唯一承载。

（六）方案六：把全部函数放主线程并依赖 Svelte 批处理

1. 这是表面实现最快但架构错误的路线。
2. Svelte 的响应式批处理只能合并状态传播和 DOM 更新，不能把同步函数执行转移到其他线程。
3. 60 个中等函数和 3 个长尾函数仍会占用主线程，输入、滚动、绘制都会被阻塞。
4. 该方案迁移成本最低，但无法满足 4 核低端机的长尾和 60fps 目标，应明确放弃。

（七）最终选型

1. 主架构采用“主线程 DAG 调度器 + 2 到 3 个 Dedicated Worker + 主线程时间切片”的混合运行时。
2. 3 个长尾函数默认进入 Worker；60 个 5 到 50ms 的纯函数通过成本模型选择 Worker 或主线程。
3. 510 个小于 1ms 的快函数默认留在主线程，以 4ms 为常规切片预算批量执行，并根据滚动和输入状态动态降低时间片。
4. 需要 DOM、主线程 API 或不可克隆状态的函数留在主线程，必须接受主线程切片约束；超过预算的函数要重构。
5. requestIdleCallback 只做预热和低优先级工作，不保证关键路径。
6. SharedArrayBuffer 不作为一期方案，只在实测证明通信瓶颈后用于局部二进制通道。
7. 放弃“全部主线程切片”，因为无法处理已经开始的 200ms 同步 CPU 任务。
8. 放弃“全部 Worker 化”，因为短任务 postMessage 不划算，DOM 函数不能迁移，且 Worker 数量和 DAG 宽度会限制收益。
9. 放弃“仅用 requestIdleCallback”，因为连续交互时没有稳定空闲时间。
10. 放弃“默认 SharedArrayBuffer”，因为安全头、HMR、序列化、死锁和调试成本与当前业务证据不匹配。

四、Svelte 5 语义正确性

（一）$state 细粒度响应如何生效

1. Svelte 5 runes 使用编译后的信号式依赖追踪；状态读取发生在文本插值、属性绑定、$derived、$effect 等响应上下文时建立依赖。
2. 对已代理的 $state 对象修改已有属性，会精确通知读取该属性的位置；替换数组或数组项时，实际更新范围取决于有哪些响应上下文读取了该数组或该 item。
3. 对深层对象和数组，Svelte 会通过响应式代理跟踪深层属性变化；但这不等价于“任意嵌套改动都导致大范围重新渲染”。
4. keyed each 配合稳定 ID 后，单条结果变化通常只更新对应行或该行内实际读取变化字段的绑定。
5. 组件不读取的字段即使变化，也不应触发该组件模板部分求值。
6. Worker 返回的普通 JSON-like 对象只在进入 $state 时被包装；不要把 Svelte proxy 传回 Worker。
7. Worker 接收的数据应是普通输入对象或 ArrayBuffer，主线程提交结果时再统一写入响应式状态。

（二）600 个结果批量写入时避免 $derived 级联

1. Worker 消息到达后先写入普通 Map<string, Result> pending cache，不在消息回调中逐节点触发 600 次 $state 赋值。
2. 每个 requestAnimationFrame 最多提交一次结果批次，或在 A 模式完成时按策略提交一次最终批次。
3. 提交时把 pending 节点转成一个最小变更集，仅更新完成的节点；失败节点进入独立错误状态。
4. $derived 应设计为纯选择器，只依赖最小必要输入，例如可见窗口 ID、排序键或具体行 ID。
5. 不在每个节点结果上挂一个 $derived 再反向通知全局集合，避免 600 个派生值逐级失效。
6. 避免在模板中直接调用执行排序、过滤或 DAG 追踪的函数；函数调用没有自动记忆，模板重跑时会重复计算。
7. 对可增量维护的派生数据，例如 Map<NodeId, Status>、索引和行列映射，应在普通模块层增量维护，然后只暴露需要响应式的版本号或可见数据。
8. $state.raw 适合持有不应深代理的大型不可变数据；对不可变快照采用替换引用，通常比让 5000 行完整数据全部变成深代理更可控。
9. 对只用于命令式同步外部系统的逻辑使用 $effect，不要用它执行 DAG 函数或级联派生业务结果。
10. 同一次事件循环任务内的多次 rune 更新通常会被 Svelte 合并到刷新周期；但仍然不应把“框架会批处理”当作随意产生 600 次无效派生和 Worker 消息的借口。

（三）表格状态形状建议

1. DAG 结果层使用普通缓存保存全部结果，避免所有业务输出都成为响应式代理。
2. 表格层使用 $state.raw 保存不可变的完整行快照，另用 $state 保存滚动起点、可见窗口、过滤条件和加载状态。
3. 可见窗口数据由一个派生选择器根据行高、scrollTop、完整行数组长度和稳定索引计算。
4. 每次批量结果到达时只替换受影响行，或生成最小不可变更新；可见区域之外的更新只改普通缓存和版本号，不立即创建 DOM 工作。
5. 如果某轮更新影响 200 个结果但只有 5 行可见，渲染提交应只包含那 5 行对应结果。
6. 滚动时只更新窗口索引和 spacer 偏移，不重新执行 200 个结果绑定。
7. 选择状态、展开状态等高频交互使用单独的小状态或 Map，不应让整个 5000 行数组深代理参与每帧更新。

（四）为什么不能照搬 React 18 的 transition 心智模型

1. startTransition 和 useDeferredValue 是 React 的并发渲染优先级与可中断协调模型，Svelte 5 没有等价的同一套 API、lane、concurrent render 或 fiber 暂停语义。
2. React transition 解决的是 React 协调和 UI 更新优先级，不会自动把同步业务函数移出主线程，也不会中断一个已经开始的 200ms CPU 循环。
3. Svelte 5 的主要优势是编译时确定细粒度更新；调用方式、失效机制、组件协调方式和可中断渲染边界都不同于 React。
4. 在 Svelte 中机械追求“标记低优先级状态”不能解决 DAG 调度、Worker 并行、结构化克隆、滚动虚拟化和取消竞态。
5. 可以借鉴“紧急输入先响应、非紧急结果稍后呈现”的优先级思想，但实现必须落在原生 Worker、rAF、切片、状态提交边界和取消协议上。
6. 如果以 React 心智设计一个巨大的 deferred 表格结果，可能导致结果延迟、过期判断和回退状态与 B 模式每字符语义混淆；题面要求每字符都触发，不代表每字符都必须重新渲染整张表。

五、风险与陷阱清单

1. Worker 与 $state 的结构化克隆边界：Worker 只能接收和返回结构化克隆支持的值，不能直接传 Svelte proxy、DOM、函数、Error 子类私有字段、Symbol 或 WeakMap；消息两端需要明确 toTransferable 与 toResult。
2. 克隆成本可能吞噬卸载收益：小函数跨线程会“计算 0.3ms、克隆和排队 2ms”，必须按节点耗时、payload 字节数和目标设备实测建立路由阈值。
3. COOP/COEP 对 Vite dev server 与 HMR 的影响：SharedArrayBuffer 需要 cross-origin isolation；要通过 Vite server.headers 加 COOP/COEP，还需验证 HMR WebSocket/source map/静态资源在隔离策略下是否正常。
4. 生产环境 headers 不属于 Vite 代码：S3、Nginx、CDN、网关或预览服务器也要设置相同策略；只在 dev server 配置会导致开发可用、生产失败。
5. SharedArrayBuffer 回退陷阱：如果 crossOriginIsolated 为 false，必须走 postMessage 或主线程切片回退，不应访问 Atomics.waitAsync 或假设共享内存可用。
6. 长尾函数在切片下仍会卡帧：主线程无法抢占普通同步函数，4ms deadline 只能决定“是否启动它”，不能在 200ms 中途停止；长尾必须放 Worker，或源码内部分块并支持取消点。
7. Worker 中已开始的同步任务也不能被普通 cancel 消息立即中断：terminate 可以结束 Worker，但会破坏其队列和运行时状态；更稳妥的是 runId 失效、空闲取消、专用长尾 Worker 隔离和合作式取消。
8. B 模式取消与副作用冲突：纯函数旧 run 结果可直接丢弃；有网络、存储、埋点、外部写入的函数被终止后可能留下外部状态，必须明确取消边界和幂等策略。
9. 竞态覆盖：第 3 个字符触发的慢任务可能晚于第 4 个字符返回，提交层必须检查 runId 或版本号，旧结果不能覆盖新输入对应的状态。
10. 输入语义不能被防抖偷换：内部可以取消旧计算，但不能把“每字符触发一轮”改为“停止输入 200ms 后才执行”；如果需求方接受延迟，应另行修改需求，而不是在实现中悄悄改语义。
11. DAG 依赖限制并行度：如果关键路径由多个 50ms 节点串成，3 个 Worker 也不能并行缩短该路径；需要展示关键路径，而不是只看 Worker 数。
12. “30% 的边不可并行”不等于 30% 工作串行：一条热点关键路径可能只占少量边，却决定总墙钟时间；边数比例不能替代节点工作量和拓扑分析。
13. Worker 数量不一定越多越好：4 核上 4 个 Worker 加主线程会造成调度争抢、GC 和热降频；滚动、合成、浏览器自身进程也需要 CPU。
14. DAG 批次饥饿：长尾节点占住 Worker 时，短小的高优先级 B 子集可能排队；需要优先级队列、独立长尾 Worker 或 work stealing，但不能破坏依赖边。
15. 失败传播必须沿 DAG 定义：一个上游失败时，依赖它的节点是跳过、接收错误、使用上次值，还是继续默认输入，不能由调度器擅自决定。
16. 5000 行 DOM 是独立瓶颈：即使所有函数 0ms，直接挂 5000 行和数万个单元格仍会造成布局、内存、样式、重排问题；不能把表格滚动 60fps 全部归因于函数调度。
17. 虚拟化的副作用：全屏查找、屏幕阅读器线性阅读、行高动态变化、sticky 列、锚点定位、打印和页面内搜索都可能受窗口化影响，需要需求确认。
18. Svelte 代理误传 Worker：把响应式对象直接 postMessage 可能触发克隆不支持、意外遍历或性能问题，跨线程边界应传 plain object 或 transferable。
19. $derived 被滥用为任务编排器：派生值必须是纯计算，不能在里面发消息、启动 Worker 或产生副作用，否则会出现重复执行和难以预测的生命周期。
20. 批量提交影响实时性：为了减少渲染把所有结果攒到最后，可能不满足实时表格语义；需要定义渐进提交频率，例如每帧一次、关键行优先或完成即提交但只提交可见行。
21. 内存与数据保留：600 个结果、每字符 run、5000 行历史和 Worker 输入若不清理，会在长时间输入后造成内存增长，需要有 run 回收和 Transferable 所有权策略。
22. 低端机热降频：冷启动一次达标不代表连续点击或长时间输入达标，验收必须包含重复运行和热机测量。
23. svelte-check 通过不代表性能通过：类型系统无法验证掉帧、Long Task、克隆耗时、DAG 关键路径或滚动 fps。
24. Worker 文件路径和 Vite 构建：需要使用打包器支持的 new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' }) 模式，并验证 dev、build、preview 三种环境。
25. 安全策略与目标环境：企业浏览器可能限制 Worker、COEP 或第三方资源；跨域字体、图片、脚本和埋点资源需要单独 CORP/CORS 处理。

六、可验证性设计

（一）验收前置

1. 使用真实 600 个函数或按真实分布构造数据，不能只用空函数微基准。
2. 记录每个节点的 id、模块、p50、p95、p99、输入字节数、输出字节数、是否可克隆、是否访问 DOM、上游和下游。
3. 输出 DAG 图的总节点数、边数、最大扇入、最大扇出、关键路径长度和每层最大并行宽度。
4. 至少覆盖冷启动、热机、连续快速输入 50 个字符、快速滚动 30 秒、A/B 混合触发、Worker 初始化前触发等场景。
5. 测试设备应包含指定的 4 核低端真机；DevTools CPU throttling 只能辅助复现，不能完全代替真机。
6. 所有指标都记录浏览器版本、设备、电源模式、网络状态、是否启用 COOP/COEP、构建模式和 commit hash。

（二）埋点设计

1. 调度器埋点字段至少包括 runId、mode、nodeId、moduleId、queueAt、startAt、endAt、workerId、thread、payloadBytes、resultBytes、cloneMs、postMs、queueMs、computeMs、stateCommitMs、cancelled、errorCode。
2. Run 级字段包括 triggerAt、firstPaintAt、lastResultAt、readyNodes、doneNodes、failedNodes、cancelledNodes、criticalPathMs、workerComputeMs、mainComputeMs、maxTaskMs。
3. 表格字段包括 scrollAt、rAFAt、rangeStart、rangeEnd、renderedRows、windowComputeMs、svelteFlushMs、layoutShift。
4. 帧监控用 requestAnimationFrame 计算相邻帧时间差，分别统计滚动、输入、A 执行和 B 执行期间的 fps、p95 帧时长和超过 16.67ms 的帧比例。
5. 使用 performance.mark 标记 run 开始、任务入队、Worker 收到、Worker 返回、状态提交、paint 完成，再用 performance.measure 计算分段。
6. 代码示例只表达埋点结构，不计入本轮实现：

```ts
performance.mark(`node:${nodeId}:queue`)
performance.mark(`node:${nodeId}:start`)
performance.mark(`node:${nodeId}:end`)
performance.measure(`node:${nodeId}:compute`, `node:${nodeId}:start`, `node:${nodeId}:end`)
```

7. Long Task 可使用 PerformanceObserver 监听，但要清楚它的阈值是 50ms：

```ts
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    reportLongTask(entry.duration, entry.startTime)
  }
}).observe({ entryTypes: ['longtask'] })
```

8. 若目标浏览器支持 Long Animation Frames，可同时监听 long-animation-frame，它比 Long Task 更适合定位样式、布局、绘制和脚本共同造成的掉帧。
9. 不引入 Web Vitals 等依赖；需要 INP 时优先使用 Chrome DevTools、真实浏览器 API 或自写事件时间埋点。
10. 所有调试埋点都应可通过编译时常量或环境开关关闭，避免测量代码本身成为负载。

（三）Performance 面板步骤

1. 以生产构建执行预览，避免开发模式和 HMR 开销掩盖问题；同时单独测试 dev server 的 COOP/COEP 与 HMR。
2. 打开 Performance 面板，CPU 设置为目标设备对应降速，网络使用本地离线或稳定内网。
3. 录制点击开始，检查主线程是否存在 50ms 以上任务、是否有连续 8ms 以上业务切片、Worker 是否真正并行、postMessage 与克隆是否集中爆发。
4. 录制快速滚动 30 秒，查看主线程是否被 DAG 计算占用，确认更新集中在可见行，Layout 和 Recalculate Style 不随 5000 行全量反复发生。
5. 录制输入框连续输入 50 个字符，确认每次 keydown 都创建 run，旧 run 结果不覆盖新 run，输入字符立即回显。
6. 查看 Rendering 面板中的 FPS、Layer Borders 和 Paint Flashing，确认滚动时只有表格窗口和必要区域重绘。
7. 检查 Memory 面板，连续输入和多次 A 触发后不允许每轮线性保留全部输入、结果和 run 对象。
8. 对比优化前后的同一场景，不允许只展示平均耗时；必须给出 p95、最长任务、掉帧率和关键路径完成时间。

（四）建议验收指标

1. npm run check 必须通过，包括 svelte-check --tsconfig ./tsconfig.app.json 和 tsc -p tsconfig.node.json。
2. npm run build 必须通过；注意它目前只执行 Vite build，不替代 check。
3. 主线程业务任务的 p95 连续执行时长小于 5ms，最大值小于 8ms；目标场景中不应出现归因于业务调度的 50ms Long Task。
4. 滚动期间帧时长 p95 小于 16.67ms，16.67ms 以上帧占比小于 2%，不能出现连续 3 帧以上超过 25ms。
5. 表格 DOM 常驻行数控制在约 40 到 60 行加 overscan，节点数由实际列数和辅助结构测量，而不是挂载完整 5000 行。
6. 滚动期间 Svelte 可见窗口更新和 DOM mutation 耗时 p95 小于 3ms，Layout 与 Recalculate Style 不应与整表规模线性增长。
7. 输入事件处理函数耗时 p95 小于 2ms，INP p95 建议小于 100ms，硬门槛小于 200ms。
8. 每输入一个字符都必须产生新的逻辑 run；可以取消或忽略旧纯计算结果，但不能通过防抖改变触发次数。
9. 最新 run 的提交结果必须全部来自当前输入版本，旧 run 覆盖率为 0。
10. Worker 通信每帧克隆、反序列化和消息分发总耗时 p95 小于 1ms；若超过预算，调整批次大小、线程路由或改用 transfer。
11. 3 个长尾函数执行期间，主线程仍能响应输入和滚动，不能出现 50ms 以上主线程阻塞。
12. A 模式完成时间以真实 DAG 的关键路径为基线，优化后的 wall time 应接近“关键路径与并行总工作”的理论下界，具体百分比目标需要拿到 DAG 后设定。
13. B 模式结果完成时间按子集规模分级设 SLA；在真实子集和输入字节数确认前，不能承诺每个字符都在 16.7ms 内完成全部结果。
14. 错误注入场景中，一个节点失败后，依赖跳过、独立节点继续、错误状态展示都符合需求方定义。
15. 连续 20 轮 A 触发和连续输入 5 分钟后，内存曲线应稳定，不能出现 run、消息、ArrayBuffer 和结果缓存线性泄漏。

（五）定位瓶颈归属的判别实验

1. 调度实验：保留 5000 行 DOM，但让 600 个函数立即返回假结果；若滚动仍掉帧，瓶颈在表格 DOM、样式、布局或 Svelte 渲染，不在函数调度。
2. 计算实验：不挂载表格或只挂载一行结果，但执行真实 600 个函数；若此时出现 Long Task，瓶颈在计算、克隆、DAG 或 Worker 协议。
3. 通信实验：Worker 中只回显输入，不执行业务计算；测量 clone、postMessage 和提交耗时，得到通信底噪。
4. 空 Worker 实验：消息到达立即返回，确认 Worker 启动和协议开销。
5. 全量 DOM 实验：临时渲染全部 5000 行并禁用计算，与虚拟窗口版本对比 Layout、Paint、内存和滚动帧时间。
6. 纯滚动实验：完全停止 DAG 调度，只滚动表格；它给出表格自身可达的 fps 基线。
7. 热机实验：连续执行 10 到 20 轮，观察 CPU 降频导致的计算时间漂移，防止冷启动数据误导容量规划。
8. 关键路径实验：只执行最长依赖链，不执行独立分支，得到 DAG 理论最短时长；再执行全部节点观察并行争抢。

七、必须追问需求方的问题

1. 3 个长尾函数是否允许修改源码，内部循环是否可以按迭代分块、检查取消点并保存中间状态？
2. 600 个函数中有多少必须访问 DOM、浏览器主线程 API、网络、IndexedDB、本地存储或可变全局单例？
3. 函数是否可视为纯函数；如果不是，取消旧 run 时已经产生的外部副作用如何回滚、忽略或幂等处理？
4. 请提供真实 DAG 的节点耗时、边表、关键路径、每层并行宽度、最大扇入扇出，以及“不可并行边”的精确定义？
5. B 模式每个字符触发的子集范围是否固定，是否包含 3 个长尾；子集结果允许的 p95 完成时间是多少？

八、最终结论

1. 一期最稳妥路线是主线程 DAG 协调器、2 到 3 个原生 Dedicated Worker、短任务主线程 4ms 切片、rAF 批量提交 $state、表格窗口化渲染。
2. 长尾函数能否保持 60fps 的关键不在 Svelte，而在于能否移出主线程或内部分块；不可修改的 200ms 同步黑盒在主线程上没有可靠抢占方案。
3. Svelte 5 负责细粒度状态到 UI 的高效更新，不负责把 CPU 密集函数自动并行化；Worker 结果应先进入普通缓存，再最小批量进入响应式层。
4. 5000 行表格必须作为独立渲染问题处理；在目标设备上应只挂载可见区域和 overscan，而不是指望函数调度器解决 DOM 规模问题。
5. SharedArrayBuffer 与 Atomics 是后续优化备选，不应在缺少真实通信瓶颈证据、部署 headers 未确认前成为基础架构。
6. 当前仍缺少 DAG、函数纯度、B 子集 SLA、表格交互和目标环境信息；这些问题回答前，最终节点路由表、完成时间承诺和是否需要 SAB 都不能定案。
