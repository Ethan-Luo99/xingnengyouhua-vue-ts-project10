一、文档信息与结论摘要

1. 本文档为 Svelte 5 + TypeScript + Vite 空白项目引入约 600 个业务函数前的纯设计阶段产物。
2. 设计目标：在 4 核低端机上，A 触发（点击一次全量执行）与 B 触发（每字符触发子集）均可交互，约 5000 行实时表格滚动保持 60fps，全程不新增任何运行时或开发时依赖。
3. 最终选型一句话：3 个 module Worker 常驻池、手写四类 postMessage 协议、主线程单函数粒度 DAG 就绪调度、每帧至多一次状态提交；requestIdleCallback 仅用于预热；SharedArrayBuffer 不进入基线。
4. 现状基线（已通过只读方式核实）：package.json 无 dependencies 字段；锁文件锁定 svelte 5.57.1、vite 8.x、svelte-check 4.x、typescript 6.x；Counter.svelte 已使用 runes 的 $state，main.ts 使用 Svelte 5 的 mount；vite.config.ts 仅注册 svelte()，无自定义 server 头；index.html 单挂载点且资源全部同源。
5. 注意事项：当前工作区 node_modules 尚未安装，本文档中关于 strict 继承链物理内容的复核需在 npm ci 后进行，且复核动作不属于本设计阶段。

三、性能预算拆解

（一）帧预算（60fps）

1. 单帧总额为 1000/60 约等于 16.7ms。低端机上浏览器内核（合成、光栅、输入派发）本身需要预留，不能把 16.7ms 全部分给业务 JS。
2. 建议切分：输入事件处理不超过 1ms；滚动相关样式、布局、绘制、合成预留 6 至 8ms（在验收机上实测回填）；业务 JS 切片目标不超过 8ms，硬上限 10ms；状态提交与 DOM 变更不超过 3 至 5ms。
3. 红线：任一主线程任务不得超过 Long Task 阈值 50ms；稳态目标为全部切片小于 10ms，给滚动帧留足余量。
4. 分工原则：A 执行期间主线程只做调度、收消息、每帧一次状态提交；CPU 计算全部移出主线程，保证滚动帧不被计算侵占。

（二）计算总量与并行度上限

1. 主线程串行计算量区间估算：510 个快函数按小于 1ms 取 0 至 510ms；60 个中值函数为 300 至 3000ms；3 个长尾为 150 至 600ms。主线程串行总量约 450 至 4110ms，不做并行必然出现数十至数百帧掉帧。
2. Worker 数量取 3：4 核留 1 核给主线程与合成线程，并用 navigator.hardwareConcurrency 兜底钳制，公式为 max(1, min(3, hardwareConcurrency - 1))。
3. Amdahl 上限：串行比例 s=0.3，核数 n=3，加速比为 1/(0.3 + 0.7/3) 约等于 1.875；理想墙钟约 240 至 2200ms。这只是乐观上限，真实值受 DAG 关键路径约束，必须在拿到真实 DAG 后重算关键路径长度。
4. 关键推论：并行不是银弹，关键路径上的串行链可能让 3 个 Worker 闲置；任务粒度必须细到单函数级并维护就绪队列，不能按 20 个模块粗粒度派发。

（三）任务切片预算（主线程调度器）

1. 每个切片执行 8ms 后主动让出；让出通道优先级为原生 scheduler.yield()（特性检测）、零延迟 MessageChannel 通知、setTimeout 回退。注意嵌套 setTimeout 存在 4ms 钳制，不能作为主通道。
2. 每帧最多处理一次收件箱排空加状态提交，挂在 requestAnimationFrame 上；若本帧是重表格更新帧则跳过计算切片，避免同帧叠加超过 16.7ms。
3. 后台标签页中 rAF 停摆、定时器被钳到 1s，因此调度不能把 rAF 作为正确性依赖，其停摆只影响吞吐。

（四）Worker 通信预算

1. 低端机单条 postMessage 两侧固定开销经验值约 0.1 至 0.5ms，因此禁止一函数一消息；Worker 内部本地攒批，约每 8ms 或每 N 个结果回传一批。
2. 结构化克隆在低端机按保守 20 至 50MB/s 估算，要求单条消息克隆耗时 P95 小于 1ms，即常规负载控制在数十 KB 量级；二进制结果使用 Transferable 转移而非拷贝，转移后主侧 ArrayBuffer 被分离，代码需显式处理所有权。
3. 消息总量估算：600 节点按每批数条至数十条合并，整轮约 60 至 300 条消息，总协议开销控制在约 50 至 150ms 且摊到多个核与多个帧上；主线程每帧只承担一次接收与一次提交，单帧协议开销小于 1ms。

（五）5000 行表格的独立预算

1. 视口内通常仅约 5 至 15 行。滚动 60fps 的关键是让屏外行不产生布局与绘制成本：content-visibility: auto 配合 contain-intrinsic-size，table-layout: fixed，滚动不挂任何做布局读写的 JS 监听。
2. 即便跳过渲染，5000 行乘以每行列数意味着 2 至 3 万个 DOM 节点，首次创建本身可达 100 至 300ms 量级；首次填充必须分批挂载，或在需求方获准后虚拟化；该成本不能与调度层混为一谈。
3. 单次 200 个结果更新，要求仅变更受影响行与文本节点，整帧 DOM 变更耗时目标小于 5ms，行节点总数不发生大规模重建，以稳定业务 key 佐证。

四、候选方案与取舍

（一）路线一：主线程宏任务切片（MessageChannel 或 scheduler.yield 加截止时间）

1. 适用性：对 510 个快函数和 60 个中值函数有效；零依赖、易调试、函数可直接访问 DOM 与闭包；strict 下无额外类型负担。
2. 失效场景：JS 无法抢占一个正在同步执行的函数。3 个长尾单次 50 至 200ms，切片器在其内部没有插桩点，单次调用即冻结 3 至 12 帧，属于结构性失效。
3. 迁移成本：低，仅需包一层执行循环与截止检查，但不能改写函数内部循环就无法治本。
4. 结论：不作为主路线，保留为 Worker 不可用时的降级路径，以及必须留在主线程的 DOM 型函数的执行方式。

（二）路线二：requestIdleCallback

1. 适用性：适合低优先级后台预热，能利用空闲期且原生零依赖。
2. 失效场景：持续滚动或连续输入期间空闲额度被压缩甚至长期不回调，无法保证 A 的完成时延与 B 的响应；timeout 兜底只能缓解饥饿；旧版 Safari 支持较晚，需按浏览器矩阵核实。
3. 迁移成本：低，但本质是尽力而为，没有优先级与抢占保证。
4. 结论：只作辅助（空闲时预热 Worker 池、运行低优先级非表格函数），不作主调度器。

（三）路线三：Web Worker 池加手写 postMessage 协议（不使用 Comlink）

1. 适用性：Vite 原生支持 new Worker(new URL('./x.ts', import.meta.url), { type: 'module' })，dev 与 build 均无需加依赖；3 个 Worker 把含长尾在内的全部 CPU 循环移出主线程，长尾执行期间主线程仍可满帧滚动；DAG 就绪节点派发、结果批量回传，协议类型可用共享 TS 类型约束，满足 strict。
2. 失效场景与成本：函数必须可脱离 DOM 与闭包运行，需要纯净性审查与 DTO 边界；跨线程数据支付克隆成本；module Worker 冷启动有几十至上百 ms，需在首屏空闲时预热；依赖数据沿硬边跨线程传递会增加延迟；调试链路变长。
3. 与 Comlink 式方案的区别：Comlink 基于 Proxy 与 RPC，会引入依赖且隐式产生大量细粒度消息，违背零依赖与攒批预算；手写协议只定义 run、result、error、cancel 四类消息，完全可控、可计数、可压测。
4. 结论：选定为主路线。它是唯一能同时解决长尾抢占、4 核利用与主线程 60fps 的零依赖方案。

（四）路线四：SharedArrayBuffer 加 Atomics

1. 适用性：固定布局的高频数值数据可零拷贝共享，Worker 间可用 Atomics 协调，对数值密集的表格列有理论吸引力。
2. 失效场景：其一，前提是跨源隔离（COOP same-origin 加 COEP require-corp 或 credentialless），需要改 Vite dev 与 preview 配置，且生产网关与 CDN 响应头可能不在前端仓库控制内，HMR 的 WebSocket 虽同源可用，但任何跨源脚本、字体、source map 都可能被 COEP 阻断；其二，600 个函数输出若为对象、字符串或变长结构，需要在 SAB 中手写 arena 序列化，收益被复杂度吃光；其三，Atomics.wait 不能在主线程阻塞，锁竞争会把并行度重新打回串行；其四，目标浏览器（中低端安卓 WebView 与旧 Safari）矩阵未知。
3. 迁移成本：最高。手工内存布局、编解码、类型断言、调试工具缺失，strict 下存在大量 unknown 与 TypedArray 断言。
4. 结论：基线放弃。仅当需求方确认数据为定长数值且能全链路开启跨源隔离时，作为某几列数据通道的后期增强，绝不承载控制面。

（五）补充路线五：长尾函数内部协程化

1. 适用性：若个别长尾函数必须留主线程（强 DOM 依赖），可将其 CPU 循环改造成每 8ms 让出的可中断协程，或把纯计算内核剥给 Worker、DOM 拼装留主线程。
2. 失效场景：需要函数源码可改且循环可切分，对第三方黑盒函数无效。
3. 结论：作为路线三的补丁手段，按函数纯净性清单逐个人工判定。

（六）最终选型与放弃理由汇总

1. 主路线：3 个 module Worker 常驻池，手写四类消息协议，主线程 DAG 就绪调度器按单函数粒度派发，表格相关节点优先。
2. 辅助手段：rAF 节拍的结果攒批提交；scheduler.yield 或 MessageChannel 切片处理主线程残留工作；requestIdleCallback 仅做预热；主线程协程化仅用于无法进 Worker 的函数。
3. 放弃纯主线程切片的理由：长尾不可抢占。
4. 放弃以 requestIdleCallback 为核心的理由：无延迟保证。
5. 放弃 SharedArrayBuffer 基线的理由：基础设施成本高、数据形态不匹配、浏览器矩阵未确认。

五、Svelte 5 语义正确性

（一）runes 下细粒度响应如何生效

1. $state 在编译期被转成信号式存储，组件模板中对某个属性的读取被编译为精确订阅；写入 results[id] = value 时，只有读过该属性的文本节点或 effect 被标记失效，不存在 VDOM 整树 diff。
2. 正确建模是结果按函数 id 建键，表格的 each 循环块使用稳定业务 key；200 个结果更新只动对应单元格，不重建 5000 行。
3. Worker 回传的是普通 DTO，在主线程完成 DTO 到状态的映射后才进入响应式边界；禁止把 Svelte 代理对象直接 postMessage。

（二）600 结果批量写入如何避免 $derived 级联重复求值

1. Svelte 5 的 $derived 是惰性、带脏标记的记忆化值：同一轮内无论同步写 1 次还是 600 次，派生值只在被读取且自上次计算后有脏标记时重算一次；$effect 每轮微任务刷新只调度一次。同一同步执行上下文内连续写 600 个属性，天然只产生一次失效传播。
2. 真实风险来自跨宏任务写入：Worker 消息分多批到达，若收到一条就直接写 $state，会触发多次刷新与多帧 DOM 变更。正确做法是双缓冲，即用非响应式普通 Map 按轮次暂存结果，rAF 回调每帧只做一次提交。
3. 提交形式建议：大表使用 $state.raw 持有行数组快照，不做深度代理，提交时以浅不可变方式替换（数组新引用、未变行对象保持身份、变更行替换对象），配合 keyed each 精确更新；小而散的标量结果用普通 $state 按 id 属性写入。两者都保证一帧一次提交、派生值一轮一次重算。
4. 编码纪律：$derived 只放纯聚合，避免派生链多层串联；非响应式簿记用 untrack；绝不在派生值里触发写入。

（三）为什么照搬 React 18 的 startTransition 或 useDeferredValue 是错误方案

1. 机制错配：transition 推迟的是 React 的整子树 render 加 reconciliation 工作量；Svelte 5 没有 VDOM render 阶段可推迟，状态写入直接映射为定点失效与定点 DOM 更新，不存在可供 transition 让步的大块渲染。
2. 调度器错配：React 并发能力与其内部 lane 调度器、可中断渲染深度耦合；Svelte 的刷新模型不提供对应 API，手造延迟赋值只是显式缓冲换了个名字，不带来公平性与抢占保证。
3. 瓶颈错配：transition 不把 CPU 移出主线程，3 个 200ms 同步循环在 React 模型里同样阻塞渲染与提交；真正解法是 Worker，借用 React 心智模型会掩盖用户态 JS 不可抢占同步函数这一真问题。
4. 语义错配：B 的要求是精确取消旧轮、仅提交新轮，transition 保留旧 UI 直到新值就绪且可能被打断，不是需求语义；Svelte 5 的正确对应物是显式轮次令牌与提交门控，而非框架魔法。

六、风险与陷阱清单

1. Worker 与 $state 之间结构化克隆的边界：闭包、DOM 节点、函数、class 实例（含方法与原型）、除 MessagePort 外的宿主对象不能克隆；Date、Map、Set、ArrayBuffer、普通对象与循环引用可克隆但按深拷贝付费；大 ArrayBuffer 应 transfer 并意识到转移后原缓冲被分离。对策：在主从两侧定义窄 DTO 类型，Worker 只暴露纯函数模块，结果用扁平对象或定长 TypedArray，DTO 到 $state 的映射只发生在主线程；禁止把任何 Svelte 代理对象塞进消息；用压测确认当前 Svelte 与 Vite 版本组合下无意外序列化路径。
2. COOP/COEP 对 Vite dev server 与 HMR 的影响：仅在使用 SharedArrayBuffer 时才必须开启，本基线不使用故不承担该成本。一旦开启，需要给 Vite 的 server.headers、preview 与生产反向代理同时配置 Cross-Origin-Opener-Policy: same-origin 与 Cross-Origin-Embedder-Policy: require-corp；HMR 的 WebSocket 同源通常不受影响，但 dev 下动态加载模块、source map、任何跨源字体或脚本会因缺少 CORP 被阻断，排查成本高且生产响应头可能不归前端团队控制。
3. 长尾函数在切片策略下仍卡帧的兜底：切片只能在函数边界让出，50 至 200ms 单函数在主线程执行时切片完全失效。兜底顺序为：首选进 Worker 整体执行；不能进 Worker 的则把纯计算内核剥离进 Worker；仍不行则改造内部循环为可中断协程，把 200ms 拆成约 20 个 8ms 片；黑盒函数要求需求方接受其执行窗口掉帧或安排重写。验收时以 Long Task 观测确认无单个长任务。
4. 每字符触发场景下的取消与竞态语义：不取消在途 Worker 任务（Atomics 中断不可移植、硬终止 Worker 成本高），而采用令牌与门控：每轮生成单调递增 runId，调度器丢弃旧轮的新派发；Worker 回传结果带 runId，主线程只提交最大有效轮次的结果，旧轮结果在双缓冲层直接丢弃；若新输入是旧输入子集，可保留可复用中间结果做缓存，但缓存正确性需 DAG 静态化支撑。连续输入期间在同一任务循环帧内合并派发，并明确 compositionstart 与 compositionend 组合态下是否触发。语义红线：可取消的是结果采纳与剩余派发，不是在途同步计算；B 的每字符触发事件语义保持不变。
5. DAG 依赖与并行度上限的冲突：30% 硬边意味着关键路径可能很长，3 个 Worker 长期只有 1 个有就绪任务，加速比远低于 Amdahl 理论值。对策：构建期做静态拓扑与关键路径分析，关键路径节点优先派发并尽量锁定同一 Worker 以减少数据搬运；跨硬边传递大结果优先 transfer；就绪队列按关键距离加是否绑定表格排序；若实测并行度长期为 1，需向需求方回传加 Worker 解决不了串行链的结论。同时防止调度死锁：每个就绪节点只派发一次，失败节点不无限重试。
6. 5000 行 DOM 与调度层无关的独立瓶颈归属判定：若关掉全部计算（空结果回放）滚动仍掉帧，问题在渲染层，处置为 keyed each、避免单元格内响应式过细、table-layout: fixed、content-visibility 或虚拟化，调度层不动；若空滚动流畅而执行期掉帧，问题在提交与消息层（批量过大或提交过频）；若只在长尾运行时掉帧，说明该函数误入主线程。判定手段为固定数据集离线回放，分别测量无计算基线、纯计算不渲染、计算加渲染三条曲线。
7. Worker 生命周期与环境差异：module Worker 在旧 WebView 与旧浏览器的支持需按矩阵核实；冷启动与模块重复打包体积需用 Vite worker 产物报告检查；生产 CSP 若限制 worker-src 会直接阻止 Worker 创建，需部署侧确认；必须设计 Worker 构造失败时的主线程切片降级路径。
8. 内存与 GC 抖动：每批消息克隆与高频 B 触发会产生大量短命对象，GC 尖峰可造成掉帧。对策：批大小固定、TypedArray 缓冲复用、行对象就地替换而非整表重建、环形埋点缓冲限长、表格保留行数设上限策略。
9. 时钟与测量误差：部分浏览器对 performance.now() 精度做钳制，切片截止时间需做钳制兼容；禁止用 setTimeout 延迟推导任何性能结论。

七、可验证性设计

（一）前置检查

1. npm ci 后执行 npm run check，确认 svelte-check 与 tsc 两段均零错误；这是入门线，不是性能验收线。

（二）自写埋点（零依赖，使用 performance.mark 与 performance.measure）

1. 调度埋点：记录每轮 runId、触发类型（A 或 B）、输入序号、派发数、取消数、各任务等待时长、执行时长、批大小、消息往返时长，写入限长环形缓冲，挂到 window.__perf 供面板读取，不接入任何响应式状态。
2. 主线程切片埋点：切片包裹 slice:start 与 slice:end 标记；提交包裹 commit:start 与 commit:end；消息接收标记 msg:in。
3. 提交计数：用一个由表格结果驱动的计数器记录每帧实际提交次数，验证每帧至多一次提交。
4. 断言式验收：构造合成数据集（510 个 0 至 1ms、60 个 5 至 50ms、3 个 50 至 200ms 函数），A 连续跑若干轮；B 模拟每 16ms 一个字符连续输入 30 字符并人为制造回包乱序，脚本校验仅最新轮结果生效、无旧值闪烁。

（三）Performance 面板测量步骤

1. 设备条件：CPU 4 倍节流或目标真机，关闭浏览器扩展；A 场景录制从点击到 5000 行填充完成的全过程。
2. 检查项：Main 轨道无超过 50ms 的长任务，无持续红色掉帧区间；长尾函数火焰图出现在 Worker 轨道；commit 相关 measure 每帧不超过 1 次且小于 5ms；录制中持续拖动表格时 FPS 稳定 60，无连续超过 3 帧低于 55fps；Layout 与 Recalc Style 范围仅限变更行，不出现整表范围。
3. 分场景录三段：只滚不动算（基线）、只算不滚、边算边滚，对比定位瓶颈归属。

（四）Long Task API 与运行时计数

1. 用原生 PerformanceObserver 监听 longtask，在测试页累计任务数与总时长；验收标准为 A 整轮与 B 连续输入期间主线程 longtask 数均为 0。
2. Worker 侧任务耗时由埋点上报，确认 3 个长尾不落在主线程。
3. 用 performance.memory（Chromium 系，仅作趋势参考）对比连续 100 轮 B 后堆内存是否回落，检查泄漏与缓冲无限增长。

（五）量化验收指标（建议与需求方确认后冻结）

1. 滚动：边执行边快速滚动 10 秒，平均 FPS 不低于 58，不出现连续 3 帧低于 50；主线程任意单任务不超过 50ms。
2. A 场景：记录整轮墙钟实测值并与关键路径理论值对比；主线程 JS 累计时长占比小于 30%，其余在 Worker。
3. B 场景：连续每字符输入下，从最后一次字符到最终结果可见的 P95 设阈值（建议先量基线再定，如小于 150ms）；任意时刻界面只展示最新一轮结果；中间轮结果提交次数为 0 或可忽略。
4. 消息与提交：单条 postMessage 处理 P95 小于 1ms；每帧提交恰好 0 或 1 次；200 行更新的提交加 DOM 帧成本小于 5ms。
5. 回归方式：合成数据集纳入开发自测脚本（纯静态页加控制台断言），不引入任何依赖。

八、必须追问需求方的问题

1. 600 个函数是否为纯函数：哪些读 DOM、localStorage、模块级可变状态或浏览器 API？不纯函数有多少、能否重构？这决定 Worker 覆盖率与主线程协程化工作量。
2. 函数输出的精确 schema 与单结果大小分布是什么？是否含二进制或大数组、字符串长度分布如何？200 个表格函数的结果是否作为其他函数的下游输入？这决定克隆、transfer 与缓存策略。
3. A 场景从点击到全部完成的可接受时延是多少？B 场景是每次按键后必须看到一次中间结果，还是只要求停止输入后快速收敛？是否存在 IME 中文输入组合期的语义要求？
4. 目标设备与浏览器矩阵具体是什么（安卓 WebView 版本、iOS 与 Safari 版本、是否桌面内嵌 Chromium）？能否保证 module Worker、scheduler.yield、performance.memory 可用？生产环境是否可下发 COOP/COEP 头（即便基线不用 SAB 也需明确否决权归属）？
5. 5000 行是否允许虚拟化（只渲染视口加缓冲行）？行高是否固定、单元格是否含富文本、图片或可编辑控件？实时是允许每帧增量更新还是必须整批原子翻页？
6. DAG 是否在构建期静态已知（可离线拓扑与计算关键路径），还是运行时动态生成边？30% 硬边的准确含义是数据依赖必须等待，还是顺序敏感不可重排？函数是否允许重试、出错对整轮的契约是什么？
7. B 的子集与全量集的重叠关系如何，子集结果能否被后续轮次复用缓存？需求方接受旧结果保留直到新值逐格替换，还是整表锁定或置 loading？这决定取消语义的用户可见行为。
8. 长尾函数源码是否可改（能否剥离计算内核或切分循环），还是黑盒只能整体调用？
